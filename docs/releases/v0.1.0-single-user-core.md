# v0.1.0 — Single-User Core

Tag: `v0.1.0-single-user-core` · Date: 2026-10-04

Single-user core release complete and checkpointed. This document is the starting point for the next phase: it says what exists,
what was tested, what is not done, and where to continue, so the repository does not have to be re-analysed.

## Purpose

A permission-controlled computer-use agent for **one user on one Windows machine**. The user states a goal in natural language; the
agent plans, acts through typed tools, verifies the real state of the machine, and reports truthfully. This release freezes the
single-user core after two live validation campaigns and a hardening iteration.

It is not multi-user, multi-tenant, distributed, horizontally scalable, highly available or internet-scale, and it does not schedule
recurring work.

## Architecture in one screen

```
User ─▶ React dashboard ─▶ REST / WebSocket API (FastAPI, loopback, bearer token)
     ─▶ TaskRuntime (one task at a time, idempotent start, pause / cancel / STOP)
     ─▶ Planner (LLM → structured plan → deterministic validation → one repair)
     ─▶ StepExecutor ─▶ ToolRouter ─▶ PermissionEngine (+ approval) ─▶ Tool ─▶ Observation
          │   tool steps: no model call        adaptive steps: bounded tool-calling loop
          └─ Recovery (classified, bounded) ─▶ re-plan (cannot relax success criteria)
     ─▶ VerificationEngine (deterministic contracts) ─▶ TaskResult
          status/outcome · verification_status · answer_status · metrics
     ─▶ Repository (memory | SQLite | PostgreSQL) + event timeline
```

input and output schemas · user-goal preservation across re-plans · deterministic tool execution · Playwright browser automation with
structured perception · Windows UI Automation · filesystem tools · controlled terminal (no shell) · permission engine and approval
workflow · prompt-injection defences · search router with provider abstraction, browser-search fallback and automation-block

## Baseline performance (single user, `openai/gpt-4.1` via OpenRouter)

| Task class | LLM calls | Tool calls | Time |
|---|---|---|---|
| Deterministic one-plan tasks (page title, count, search, allow-once delete) | 1–2 | 1–2 | 5–15 s |
| File organization | 3 | 4 | 10 s |
| Summaries of a page or file | 2–3 | 1–2 | 8–12 s |
| Calculator through UI Automation | 7 | 8 | 22 s |
| Dynamic page (find / click / read) | 8 | 8 | 28 s |
| Five-page navigation with a pause | 2 | 10 | 33 s |
| Vision fallback | 4 (+1 vision) | 3 | 18 s |
| Blocked browser search → API search | 14 | 11 | 59 s |

Re-plans 0–1, recoveries 0–2, verification under 0.1 s per task, estimated cost $0.015–0.11 per task. Single runs.

## Security status

Controls reviewed and covered by tests: filesystem allowlists, traversal, junction/symlink, UNC/device/ADS paths, protected
locations, terminal restrictions, browser isolation, SSRF, download restrictions, injection detection and taint, secret redaction,
API token, WebSocket authentication, Host/Origin validation, approvals, limits, kill switch, audit. No secrets in the tree or in Git
history (test fixtures only). Open limitations are listed in [SECURITY.md](../../SECURITY.md) and are not claimed solved.

## Limitations and known issues

* One live model, short tasks, single runs. No multi-model comparison.
* `verified` is only as strong as the plan's success criteria; free-text adaptive answers are not checked for completeness.
* Adaptive steps usually spend one model call per action.
* Official-source check is "on the stated domain".
* A task does not survive a process restart. Time spent paused counts towards the execution limit.
* Windows-only desktop automation; sparse UI Automation trees untested; stale-reference recovery not exercised live.
* Heuristic injection detection; approved code runs with the user's privileges; no TLS, per-user auth or rate limiting.
* No `LICENSE` file.

## Reproduce the environment

```powershell
.\scripts\setup.ps1                      # venv + dependencies + frontend packages
copy .env.example backend\.env           # then set SAA_SECURITY__API_TOKEN, SAA_LLM__PROVIDER / MODEL / API_KEY
cd backend
.\.venv\Scripts\python.exe -m app doctor
.\.venv\Scripts\python.exe -m app llm-check
cd ..
.\scripts\check.ps1                      # full deterministic validation
.\scripts\run.ps1                        # UI + API on http://127.0.0.1:8000
```

Live scenarios (real model, real Chrome and desktop, sandbox data under `~/SmartAIAssistant/validation`):

```powershell
cd backend
.\.venv\Scripts\python.exe -m validation.campaign list
$env:SAA_CAMPAIGN_TAG = "mytag"; .\.venv\Scripts\python.exe -m validation.campaign run PB
```

Requirements: Windows 10/11, Python 3.11+, Node 20+, Chrome or Edge, an LLM API key. `backend/.env` and local databases are ignored
by Git.
